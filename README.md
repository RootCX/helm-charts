# RootCX Helm Chart

Install RootCX on Kubernetes or OpenShift with one Helm chart. Portal, Core and
PostgreSQL run as separate workloads and are connected through OIDC over HTTPS.

## Prerequisites

- Kubernetes 1.28+ or OpenShift with the Route API
- Helm 3.14+
- a default `ReadWriteOnce` StorageClass when using embedded PostgreSQL

## Add the repository

```bash
helm repo add rootcx https://rootcx.github.io/helm-charts
helm repo update
```

## OpenShift Local

This is the tested local quick start. It uses OpenShift Local's
`*.apps-crc.testing` DNS and a locally trusted certificate generated by
[mkcert](https://github.com/FiloSottile/mkcert).

```text
Portal  https://portal.rootcx.apps-crc.testing
API     https://api.rootcx.apps-crc.testing
```

### 1. Install mkcert

```bash
# macOS
brew install mkcert

# Windows
choco install mkcert
```

For Scoop and Linux, follow the
[official mkcert installation guide](https://github.com/FiloSottile/mkcert#installation).

### 2. Create the local certificate

```bash
kubectl config use-context crc-admin
kubectl create namespace rootcx

mkcert -install
mkcert -cert-file rootcx-local.crt -key-file rootcx-local.key portal.rootcx.apps-crc.testing api.rootcx.apps-crc.testing

kubectl create secret tls rootcx-local-tls --namespace rootcx --cert=rootcx-local.crt --key=rootcx-local.key
```

Give Core the public mkcert CA.

macOS, Linux, WSL or Git Bash:

```bash
kubectl create configmap rootcx-local-ca --namespace rootcx --from-file=ca-bundle.crt="$(mkcert -CAROOT)/rootCA.pem"
```

Windows PowerShell:

```powershell
$ca = mkcert -CAROOT
kubectl create configmap rootcx-local-ca --namespace rootcx "--from-file=ca-bundle.crt=$ca/rootCA.pem"
```

Only `rootCA.pem` enters the cluster. Never copy or share `rootCA-key.pem`.

### 3. Install RootCX

Download the tested local values:

```bash
curl -fsSLo values.yaml https://raw.githubusercontent.com/RootCX/helm-charts/master/examples/values-openshift-local.yaml
```

Install and verify:

```bash
helm upgrade --install rootcx rootcx/rootcx \
  --namespace rootcx \
  --values values.yaml \
  --wait \
  --timeout 10m

kubectl get pods --namespace rootcx
helm test rootcx --namespace rootcx --logs
```

Open [https://portal.rootcx.apps-crc.testing](https://portal.rootcx.apps-crc.testing)
and register `admin@rootcx.localhost`.

Restart the browser if it was open during `mkcert -install`.

## Production

Production requires:

- two DNS names pointing to the ingress controller or OpenShift router;
- a trusted certificate covering both names;
- explicit application secrets and a bootstrap administrator email.

The examples below use `portal.example.com`, `api.example.com` and a certificate
covering both names. A wildcard such as `*.example.com` is also valid for those
two hosts.

### 1. Prepare production values

Download the file for your platform and save it as `values.yaml`:

- [Kubernetes values](examples/values-kubernetes.yaml)
- [OpenShift values](examples/values-openshift.yaml)

Replace every `REPLACE_WITH_...` value in `values.yaml`. The chart rejects an
incomplete production configuration. Run `openssl rand -hex 32` separately for
each secret placeholder; never reuse one generated value for another secret.

Generate the OIDC signing key and keep it outside version control:

```bash
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048 -out oidc-private-key.pem
chmod 600 oidc-private-key.pem
```

### 2. Configure HTTPS

Create the namespace once:

```bash
kubectl create namespace rootcx
```

Skip this command if the namespace already exists.

#### Kubernetes

An [Ingress controller](https://kubernetes.io/docs/concepts/services-networking/ingress/#prerequisites)
must already be installed. Create the TLS Secret named by
`global.rootcx.tls.secretName` with the certificate chain and matching key:

```bash
kubectl create secret tls rootcx-tls --namespace rootcx --cert=fullchain.pem --key=privkey.pem
```

Set the correct `ingress.className` and `core.ingress.className` in
`values.yaml` for your cluster.

#### OpenShift

The simplest production setup uses the router's default wildcard certificate.
Leave `global.rootcx.tls.secretName` empty when that certificate covers both
Route hosts and is trusted by every client.

To use a certificate stored in the application namespace, use an OpenShift
version where [externally managed Route certificates](https://docs.redhat.com/en/documentation/openshift_container_platform/4.20/html/ingress_and_load_balancing/routes)
are supported for production. Verify the API first:

```bash
kubectl explain route.spec.tls.externalCertificate
```

Then create the TLS Secret named by `global.rootcx.tls.secretName`:

```bash
kubectl create secret tls rootcx-tls --namespace rootcx --cert=server.crt --key=server.key
```

The chart creates namespace-scoped RBAC granting the OpenShift router read-only
access to this Secret. On OpenShift 4.18 and earlier this capability is a
Technology Preview; use the default router certificate instead. It is Generally
Available on OpenShift 4.19 and later.

For an enterprise CA, every browser and workload must trust that CA. If Core
connects to an endpoint signed by it, create a CA ConfigMap:

```bash
kubectl create configmap rootcx-enterprise-ca --namespace rootcx --from-file=ca-bundle.crt=enterprise-ca-chain.pem
```

Then set:

```yaml
core:
  trustedCA: rootcx-enterprise-ca
```

Leave `core.trustedCA` empty for public CAs already trusted by the container.

### 3. Install RootCX

```bash
helm upgrade --install rootcx rootcx/rootcx \
  --namespace rootcx \
  --values values.yaml \
  --set-file oidc.signingKey=oidc-private-key.pem \
  --wait \
  --timeout 10m
```

Verify the release:

```bash
kubectl get pods --namespace rootcx
helm test rootcx --namespace rootcx --logs
```

Then open the Portal hostname configured in `values.yaml` and register the
configured `bootstrap.adminEmail`.

## Production notes

- SMTP is optional. Portal starts normally when `email.enabled` is `false`.
- Embedded PostgreSQL is intended for local or single-node installations. Use
  an externally operated PostgreSQL service when production requires high
  availability, managed backups or point-in-time recovery.
- Keep credentials and private keys out of version control. The chart supports
  `existingSecret` for Portal and `core.existingSecret` for Core.
- Certificate issuance and renewal are external to this chart. Keep the same
  Secret name when a platform certificate manager renews a certificate.
- Add private endpoints blocked by the default NetworkPolicy explicitly under
  `core.networkPolicy.extraEgress`; never use guessed domains or CIDRs.

See [`values.yaml`](charts/rootcx/values.yaml) for all configuration options.
